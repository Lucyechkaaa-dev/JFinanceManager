# JFinanceManager

Фінансова система з обліком транзакцій: рахунки в кількох валютах, перекази між
користувачами з конвертацією за курсом НБУ, незмінний журнал транзакцій (тип, сума, дата, опис),
обчислення балансу рахунку з журналу, сторно, аудит, виписки в CSV і JSON.

Проєктна документація — [SDD.md](SDD.md): вимоги, NFR, Definition of Done, діаграми, ризики.

## Запуск

Потрібні JDK 21+ і Maven 3.9+.

```bash
mvn clean package          # збирання + усі тести
mvn test                   # лише тести
mvn clean verify           # тести + Checkstyle + SpotBugs + поріг покриття JaCoCo (70 %)
mvn test-compile org.pitest:pitest-maven:mutationCoverage   # мутаційне тестування

java -jar target/jfinance-manager-1.0.0-SNAPSHOT.jar
```

Swagger UI: http://localhost:8080/swagger-ui.html

| Змінна середовища | За замовчуванням | Призначення |
|---|---|---|
| `JFINANCE_DB_PATH` | `jfinance.db` | файл SQLite |
| `JFINANCE_ADMIN_USERNAME` | `admin` | логін першого адміністратора |
| `JFINANCE_ADMIN_PASSWORD` | *(порожньо)* | його пароль; якщо порожньо — генерується й **один раз** пишеться в лог |

Перший адміністратор створюється лише тоді, коли таблиця користувачів порожня. Паролів у
репозиторії немає: у тестах пароль адміністратора випадковий на кожен запуск.

## Що вміє

| FR | Можливість | Ендпоінт |
|---|---|---|
| FR-1 | Реєстрація та вхід (сесія `JSESSIONID`, 15 хв) | `POST /api/auth/register`, `/login`, `/logout`, `GET /api/me` |
| FR-2 | Рахунки в UAH, USD, EUR, GBP, PLN (по одному на валюту) | `GET/POST /api/accounts` |
| FR-3 | Поповнення адміністратором | `POST /api/admin/accounts/{id}/deposit` |
| FR-4 | Переказ з описом | `POST /api/transfers` |
| FR-5 | Конвертація за курсом НБУ, обмін між власними рахунками | `POST /api/transfers` з `toCurrency`, `GET /api/rates` |
| FR-6 | Історія за період, виписка CSV або JSON | `GET /api/transactions?from=&to=`, `GET /api/transactions/export?format=csv\|json` |
| FR-7 | Баланс, обчислений з журналу, і звірка зі збереженим | `GET /api/accounts/{id}/balance`, `GET /api/admin/accounts/{id}/balance` |
| FR-8 | Блокування, ролі, сторно, аудит | `PATCH /api/admin/users/{id}/status\|role`, `POST /api/admin/transactions/{id}/reverse`, `GET /api/admin/audit` |

Приклад переказу з конвертацією:

```json
POST /api/transfers
{ "fromCurrency": "UAH", "toUsername": "taras", "toCurrency": "USD",
  "amount": "451.06", "description": "Оплата за квартиру" }
```

Якщо `toUsername` — ви самі, це обмін між власними рахунками (`EXCHANGE`).
Помилки повертаються у форматі RFC 9457 (`application/problem+json`): 400 — некоректний ввід,
401/403 — немає доступу, 404 — не знайдено, 409 — конфлікт, 422 — порушено бізнес-правило
(наприклад, нестача коштів), 423 — акаунт тимчасово заблоковано.

## Архітектура

Пакети за функціональністю: `auth`, `user`, `account`, `transaction`, `transaction.export`,
`exchange`, `admin`, `audit`, `common`. Контролер → сервіс → репозиторій (інтерфейси Spring
Data, за якими стоїть SQLite через JDBC/Hibernate). Діаграми — у [SDD.md](SDD.md).

## Патерни проєктування

### Builder (породжувальний) — `AuditEntry.Builder`
**Біль:** запис аудиту має шість полів, з них три рядки підряд (`actor`, `target`, `details`),
і в позиційному конструкторі їх легко переставити — компілятор не помітить, а в аудиті
опиниться неправда. **Де:** `audit/AuditEntry.java` (клас `Builder`), використовується в
усіх сервісах через `auditService.record(AuditEntry.builder().actor(..).action(..)...)`;
`build()` перевіряє обов'язкові поля й обрізає `details` до 512 символів. **Без нього:** 13
викликів `new AuditEntry(a, b, c, d, true, now)` з ризиком переплутати аргументи та
продубльованою перевіркою довжини.

### Adapter (структурний) — `NbuExchangeRateProvider`
**Біль:** API НБУ віддає JSON-масив із власними назвами полів, датою `dd.MM.yyyy` і
не-ISO кодами (метали), а бізнес-логіці потрібні просто «курси до гривні». **Де:**
`exchange/NbuExchangeRateProvider.java` перетворює відповідь НБУ на `ExchangeRates` і реалізує
інтерфейс `ExchangeRateProvider`, з яким працює `CurrencyConverter`. **Без нього:**
`CurrencyConverter` і `TransferService` знали б про HTTP, формат дат і структуру JSON НБУ,
а тести переказів залежали б від мережі (зараз підставляється `FixedRatesConfig`).

### Decorator (структурний) — `CachingExchangeRateProvider`
**Біль:** НБУ не можна смикати на кожен переказ (NFR-3: ≤ 1 запит на 60 хв), а при його
недоступності перекази не мають зупинятися. **Де:** `exchange/CachingExchangeRateProvider.java`
обгортає будь-який `ExchangeRateProvider`, додає кеш і fallback на останній курс; зібрано в
`exchange/NbuClientConfig.java`. **Без нього:** кеш і fallback жили б усередині адаптера НБУ
(так і було до рефакторингу), клас мав би три причини для зміни, і для іншого джерела курсів
кешування довелося б писати заново.

### Strategy (поведінковий) — `StatementExporter`
**Біль:** виписку потрібно віддавати в різних форматах, а новий формат не має вимагати
правки контролера чи `switch`. **Де:** інтерфейс `transaction/export/StatementExporter.java`,
реалізації `CsvStatementExporter` і `JsonStatementExporter`, вибір за `?format=` — у
`StatementExporters`. **Без нього:** `switch (format)` у контролері, який треба правити для
кожного нового формату (XML, PDF), — порушення принципу відкритості/закритості.

## Прийняті рішення й чому

| Рішення | Чому |
|---|---|
| Гроші — `Money` (`BigDecimal` + `Currency`), у БД — `long` копійок | `double` дає помилки округлення; у SQLite немає точного `DECIMAL`. Більше 2 знаків після коми — 400. |
| Журнал транзакцій append-only, скасування — сторно (`REVERSAL`) | Історію не можна переписати; `UNIQUE(reversal_of_id)` не дає сторнувати двічі. |
| Баланс зберігається в рахунку **і** обчислюється з журналу (FR-7) | Швидке читання + можливість звірки; інваріант перевіряється тестами. |
| Конвертація округлює **вниз** | Система ніколи не зараховує більше, ніж списала (NFR-1). |
| Один пул-з'єднання з SQLite | SQLite має одного писача; так немає `SQLITE_BUSY` і гонок, тест 20 паралельних переказів. |
| Годинник тикає мілісекундами | SQLite зберігає час з точністю до мс; без цього час читався з БД інакшим, ніж записаний (знайдено тестом). |
| Argon2id, блокування після 5 спроб на 15 хв, сесія 15 хв | NFR-2. Блокування адміном діє одразу навіть для відкритих сесій. |
| Аудит пишеться в тій самій транзакції, що й операція | Немає «операції без аудиту» чи «аудиту без операції». |
| CSRF вимкнено | Браузерного клієнта немає, cookie `SameSite=Strict`; для веб-фронтенду треба ввімкнути. |
| Spring Boot + JPA замість «голого» JDBC | Менше шаблонного коду; JDBC лишається під капотом (драйвер `sqlite-jdbc`). |

## Тести

`mvn test` — 122 тести (JUnit 5, AssertJ, Mockito, MockMvc, справжня SQLite у `target/`):

- **межові значення:** списання всього балансу → рівно 0, 0,01 грн, довжина логіна 2/3/32/33,
  пароля 7/8 символів, TTL кешу «на 1 нс раніше» і «рівно», обрізання деталей аудиту 512/513;
- **порожній ввід:** порожнє тіло запиту, порожня історія, порожня виписка CSV/JSON, рахунок без
  транзакцій;
- **некоректний ввід:** битий JSON, від'ємні/нульові суми, 3 знаки після коми, невідома валюта,
  невідомий формат виписки, обернений діапазон дат, `null` в конструкторах;
- **читання з БД:** `PersistenceRoundTripIntegrationTest` записує кожну сутність, очищує контекст
  і читає рядок знову — усі поля збігаються;
- **TDD-цикли в історії git** (тест червоний → реалізація → рефакторинг): опис транзакції,
  обчислення балансу, Strategy, Decorator, Builder, точність часу в БД.

**Мутаційне тестування (PIT)** штучно ламає код (межі `<`/`<=`, умови, `null` замість
результату) і перевіряє, що тести падають. Для доменної логіки й патернів: 169 мутацій,
вбито 155 (92 %), test strength 95 %. Єдиний «вцілілий» мутант — еквівалентний (обрізання рядка
довжиною рівно 512 до 512 символів нічого не змінює).

## Якість коду

`mvn clean verify` падає, якщо падає тест, покриття рядків < 70 % (JaCoCo), є порушення
Checkstyle (Google Java Style з табами, `config/checkstyle/`) або помилки SpotBugs
(`config/spotbugs/`). Те саме запускає GitHub Actions (`.github/workflows/ci.yml`).
Відступи табами — свідоме відхилення від Google Style, конфіг адаптовано.

## Відомі обмеження

- Сесії в пам'яті одного вузла, SQLite — однокористувацька БД; для масштабування потрібні
  PostgreSQL і Spring Session.
- Тимчасове блокування після невдалих входів можна використати, щоб навмисно заблокувати
  чужий акаунт на 15 хв (компроміс, описаний у ризиках SDD).
